## Что нужно сделать (из ClickUp)

Раздел **Feedback**: два пункта — **Contact support** и **Rate app**. Не
завязан на backend OpenWebUI — нативные платформенные механизмы (in-app
review, email/support flow) плюс аккуратная обработка edge cases (недоступность
интеграции, offline, повторные тапы, ограничения устройства). Полные
требования и тест-сценарии — см. ClickUp.

## Ключевые факты по native review API

**Google Play In-App Review API (Android):**

- Есть **квота показов** — если вызывать чаще ~раза в месяц, диалог может не
  появиться вообще, и это скрыто от разработчика.
- API **не сообщает**, был ли диалог реально показан и оставил ли юзер отзыв.
- `requestReviewFlow()` **расходует квоту**, даже если потом не вызвать
  `launchReviewFlow()`.
- Google не рекомендует вешать эту API на выделенную кнопку "Оценить" — но у
  нас в дизайне именно такая кнопка, это осознанное отступление.

**iOS SKStoreReviewController:**

- Максимум **3 показа за 365 дней** на пользователя на приложение, дальше —
  silent no-op.
- Тоже **нет сигнала**, показался ли диалог и что выбрал юзер.
- Пользователь может отключить эти промпты в системных настройках.

**Практическое следствие:** т.к. "Rate app" — явное действие по тапу (не
авто-промпт после успеха), а native review API не даёт обратной связи об
успехе — нельзя реализовать "if native review fails, open store page" как
try/catch по реальному результату показа (такого сигнала нет). "Fail" в
терминах тикета = исключение самого вызова API. Рекомендованный паттерн:
попытаться вызвать native review API; если вызов упал с ошибкой/недоступен —
сразу открыть store deep-link как fallback; если вызов прошёл без исключения —
считать это успехом на уровне UI, даже если диалог мог быть тихо скрыт квотой.

**Библиотеки (2026):** Expo-проекты — `expo-store-review`; bare RN —
`react-native-in-app-review` (Android API 21+, iOS 10.3+).

Контекст: React Native клиент к OpenWebUI. В отличие от других задач эпика

Перед началом:
1. Проверь, есть ли в проекте УЖЕ интеграция support-канала (Intercom, Zendesk,

2. Проверь, используется ли уже какая-то review/rating библиотека в проекте

   предпочтителен expo-store-review; если bare RN — react-native-in-app-review.
   Не добавляй вторую библиотеку, если одна уже есть.
3. Проверь, есть ли в проекте существующий паттерн analytics-событий для

   пропсов для этих двух действий; если аналитики в settings ещё нет —
   НЕ добавляй её здесь по своей инициативе (задача говорит "if analytics

4. Узнай/найди actual App Store id (iOS) и package name (Android) проекта —

ВАЖНЫЙ КОНТЕКСТ ПО NATIVE REVIEW API (учти при проектировании флоу, это не
очевидно из дизайна/тикета):
- Google Play In-App Review и iOS SKStoreReviewController НЕ сообщают вызываю-
  щему коду, показался ли диалог реально и что выбрал пользователь. И то, и
  другое имеет скрытую квоту показов (Android: примерно раз в месяц; iOS: до
  3 раз за 365 дней), после исчерпания которой вызов API — это молчаливый
  no-op без ошибки.
- Следствие: нельзя реализовать "if native review fails, open store page" как
  try/catch по реальному результату показа — такого сигнала не существует.
  Что МОЖНО поймать как "fail" — это исключение самого вызова API (например,
  Play Services недоступны, слишком старая ОС, библиотека не смогла
  инициализироваться). Именно это и нужно трактовать как "native review
  unavailable/failed" в терминах тикета.
- Т.к. это явная кнопка в настройках (пользователь осознанно тапнул "Оценить
  приложение", а не получил мягкий промпт после успешного сценария), у него
  должно быть ощущение, что что-то произошло, даже если native API молча
  съело квоту. Рекомендуемый паттерн: попытаться вызвать native review API;
  если вызов упал с ошибкой ИЛИ библиотека сообщает о недоступности — сразу
  открыть deep-link на страницу приложения в сторе как fallback. Если вызов
  API прошёл без исключения — считать это успехом с точки зрения UI (не
  показывать доп. deep-link поверх), даже если фактически диалог мог быть
  скрыт квотой — это ожидаемое поведение платформы, а не баг.
  Если продукт/дизайн ожидает другого поведения (например, всегда открывать
  сторовую страницу вместо native review, т.к. это надёжнее для explicit
  кнопки) — уточни это как открытый вопрос, если в Figma не указано явно.

1) Contact support
- Кликабельный пункт -> открыть support-флоу, использующийся в проекте
  (см. п.1 подготовки выше). Если ничего нет — минимально: mailto: со
  адресом поддержки (взять из конфига/констант проекта, не хардкодить
  случайный email) через Linking API.
- Prefilled data (если флоу это поддерживает, например mailto с subject/body
  или support SDK с user context): подставить доступные данные пользователя/
  приложения (например email юзера — уже доступен через authApi.useGetProfile,
  версия приложения, платформа) — но не придумывай новые поля, которых нет в
  support-интеграции.
- Debounce/guard от повторных тапов: пока флоу открывается/не завершил
  инициализацию — игнорировать повторные тапы (не открывать несколько
  support-окон/email-композеров одновременно).
- Если интеграция недоступна или её открытие падает (например, на устройстве
  нет email-клиента для mailto:, Linking.canOpenURL возвращает false) —
  показать понятный fallback-текст (тост/алерт), не ломать экран настроек.

2) Rate app
- Кликабельный пункт -> запускает native in-app review, если библиотека
  поддерживает платформу и вызов не упал (см. "ВАЖНЫЙ КОНТЕКСТ" выше).
- Fallback на store-страницу при недоступности/ошибке native review:
    * iOS: deep-link вида itms-apps://itunes.apple.com/app/id<APP_ID>
      ?action=write-review (или актуальный формат из библиотеки, если она
      предоставляет готовый helper);
    * Android: market://details?id=<PACKAGE_NAME>, с фолбэком на
      https://play.google.com/store/apps/details?id=<PACKAGE_NAME>, если
      market:// схема не может быть открыта (Linking.canOpenURL false —
      например, нет установленного Google Play).
- Если и store-ссылка не открывается (canOpenURL false для обеих схем) —
  показать понятный fallback-текст, не ломать экран.
- Debounce/guard от повторных тапов, аналогично Contact support — пока флоу
  не завершится (или пока не истечёт короткий cooldown, если у выбранной
  библиотеки нет promise/callback завершения), повторные тапы игнорируются.

3) Общие edge cases (из тикета)
- Offline: если выбранный флоу требует сети (например, mailto может не
  требовать, а web-based support chat — требует) — проверить состояние сети
  (если в проекте уже есть net-info хук/утилита — использовать её) и показать
  понятное сообщение, а не зависать/крашиться.
- Device restrictions: отсутствие email-клиента, отключённые review-промпты
  в системных настройках юзера (iOS), отсутствие Play Store на устройстве —
  для всех этих случаев должен быть graceful fallback message, не silent
  failure и не краш.
- Экран настроек должен оставаться стабильным (не белый экран/креш) после
  ЛЮБОГО неудачного вызова любого из двух флоу.

- Никакого debug-вывода/ошибок в консоли в финальной версии.
